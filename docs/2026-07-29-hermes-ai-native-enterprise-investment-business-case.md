## 1. 决策摘要

### 1.1 建议批准什么

建议批准 Hermes 的**第一阶段经营价值验证**，而不是一次性批准完整企业平台。

首期只做两件能够形成真实经营证据的事情：

1. 建成商用可控的 H5/PWA、Remote Server、Connector 与 Agent Local Gateway
   最小闭环；
2. 选择一个内部高频跨系统工作流，验证“员工 Work Agent + Task Contract”
   是否能减少协调时间、缩短周期并形成可复用 Skill。

第一阶段通过后，再依次投资：

1. 低风险动作和 Agent 协作；
2. 企业知识、数据权限和核心 Skill；
3. DTC+ 外部增长闭环；
4. 多租户、私有化交付和规模化商业运营。

### 1.2 不建议批准什么

当前不建议：

- 先做覆盖全公司的 AI 大中台；
- 同时改造所有部门流程；
- 按员工 AI 使用量判断成败；
- 以内容产量、Agent 数量或自动化率作为核心 KPI；
- 在没有基线数据时承诺固定 ROI；
- 在客户经营价值尚未被证明前，提前承担完整产品化和交付体系成本；
- 为 SaaS、专有云、私有化和离线版维护多套业务代码。

### 1.3 投资判断

Hermes 值得投资的原因，不是“AI 是趋势”，而是它有机会同时解决三类已经存在的
经营成本：

| 经营成本 | 现在如何发生 | Hermes 的作用 | 最终验证指标 |
|---|---|---|---|
| 协调成本 | 员工跨系统寻找、复制、确认、等待 | Agent 组织任务，服务端路由协作，自动形成状态和证据 | 周期、等待时间、吞吐量、返工率 |
| 能力流失 | 经验留在人、聊天和临时文档中 | 将有效实践沉淀为带 Owner、版本和权限的知识与 Skill | 复用率、新人达标时间、结果一致性 |
| 增长割裂 | 内容、广告、电商、零售和客户数据分别优化 | 以客户、贡献毛利和复购为共同结果组织 DTC+ 工作流 | 增量贡献毛利、CAC、复购、库存周转 |

但机会不等于已实现价值。外部研究显示 AI 收益高度依赖任务、人员和工作流；
因此本方案的核心不是“先相信”，而是用阶段门禁把不确定性逐步买下来。

### 1.4 建议的首笔授权

建议只批准 **Gate 0 + Gate 1**：

| 项目 | 建议范围 |
|---|---|
| 周期 | 12–16 周 |
| 投入 | 12–20 人月 |
| 外部现金支出 | 云资源、模型、安全测试和必要第三方服务，设硬上限 |
| 试点范围 | 1 个内部工作流、30–80 名真实员工、2–4 个既有系统 |
| 技术范围 | 只读优先，最多开放 1–2 个低风险可回滚动作 |
| 核心结果 | 证明周期缩短、有效采纳、结果质量和单位成本 |
| 决策结果 | GO、CONDITIONAL、HOLD 或 STOP |

若按全成本人员单价 `C = 3.5 万元/人月`、首期外部支出 `5–20 万元`估算，
首笔授权区间约为：

```text
首期投资 = 12–20 人月 × C + 5–20 万元
         = 47–90 万元
```

这只是用于审批的示例口径，不是报价。正式预算必须使用本公司的真实人员全成本、
采购报价和税费重算。

## 2. 需要解决的经营问题

### 2.1 问题不是系统不够，而是工作没有形成闭环

多数企业已经拥有 CRM、ERP、OA、项目、客服、BI、知识库和内容工具。新增一个
AI 对话框不会自然消除以下问题：

- 同一个客户或项目在多个系统中存在不同事实；
- 员工需要反复搜索、复制、整理和解释上下文；
- 工作状态依靠聊天追问，责任和完成标准不清楚；
- 报表能描述发生了什么，却不能直接组织下一步行动；
- 经验通过口头传授，人员变化后能力重新建设；
- 业务变化需要排期改页面和流程；
- 每次系统集成都形成新的接口、脚本和维护责任；
- 外部营销环节分别追求曝光、点击、成交，不能解释利润和复购。

这是一类“协调与能力复用”问题，不只是生成内容的问题。

### 2.2 不做的成本如何计算

不能用抽象的“数字化落后”作为投资理由。应在 Gate 0 形成以下基线：

| 成本对象 | 取数方法 | 财务映射 |
|---|---|---|
| 寻找信息 | 时间抽样、任务日志、员工访谈 | 可释放产能 |
| 重复录入 | 系统事件和任务观察 | 可释放产能、差错成本 |
| 等待和催办 | Work Item 时间线 | 交付周期、现金回收时间 |
| 返工和纠错 | 退回、重开、补件记录 | 人力成本、客户损失 |
| 新人学习 | 达到独立交付标准的时间 | 培训和机会成本 |
| 专家重复答疑 | 专家工时和问题重复率 | 关键人才产能 |
| 系统维护 | 变更工单、接口故障和发布工时 | IT 现金成本 |
| 营销浪费 | 渠道、活动、订单和毛利数据 | 可避免投放损失 |
| 客户流失 | 复购、投诉、服务和退货数据 | 留存收入和毛利 |

若这些数据没有被测量，任何 ROI 都只是意见。

### 2.3 什么情况下不值得做

出现以下情况时，不应启动企业级 Hermes 投资：

- 仅有少量员工需要文案、翻译或摘要；
- 目标工作已被单一 SaaS 完整解决；
- 任务频率低，且每次都高度非结构化；
- 没有业务 Owner 愿意为结果负责；
- 没有数据 Owner，关键事实无法确认；
- 企业不允许调整原有工作流程；
- 无法定义成功、失败和停止条件；
- 节省时间后没有新的产出、成本替代或增长承接方式；
- 只是希望通过 AI 监控员工；
- 只是因为竞争对手宣布了 AI 战略。

此时购买标准 AI 账号或继续使用现有系统，通常比建设企业工作台更合理。

### 2.4 什么情况下值得进入验证

满足越多条件，Hermes 的投资成立概率越高：

- 一个工作流需要跨 3 个以上系统；
- 涉及多个角色、频繁等待或反复确认；
- 每月重复发生，且结果可以衡量；
- 企业拥有 50 名以上知识型员工或大量外部协同人员；
- 专家经验是业务瓶颈；
- 数据和动作存在明确权限要求；
- 需要私有化、审计或本地 Agent 执行；
- 业务变化快，固定页面持续产生改造成本；
- 外部增长需要打通内容、渠道、成交和复购；
- 企业希望把有效做法转化为长期可复用资产。

## 3. 外部研究能够证明什么

### 3.1 证据矩阵

| 研究 | 样本与场景 | 主要结果 | 对本项目的支持 | 不能据此承诺什么 |
|---|---|---|---|---|
| [NBER / QJE：Generative AI at Work](https://www.nber.org/papers/w31161) | 5,179 名客服人员 | 平均每小时解决问题数提升约 14%，新手和低技能组约 34% | AI 可传播优秀实践，结构化任务有生产率机会 | 不能推导全公司提升 14% |
| [HBS AI Institute：Jagged Technological Frontier](https://aiinstitute.hbs.edu/navigating-the-jagged-technological-frontier/) | 758 名 BCG 顾问 | 在 AI 能力边界内，任务完成更快、质量更高；边界外可能变差 | 必须按任务适配并设置验证门禁 | 不能假设复杂决策都适合 AI |
| [Microsoft Research / GitHub Copilot 实验](https://www.microsoft.com/en-us/research/publication/the-impact-of-ai-on-developer-productivity-evidence-from-github-copilot/) | 受控编码任务 | 使用 Copilot 的参与者完成任务速度显著提高 | AI 对边界明确的专业任务可产生较大增益 | 不能代表完整研发周期或所有开发者 |
| [METR：资深开源开发者随机实验](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) | 熟悉自身仓库的资深开发者 | 2025 年初工具条件下，使用 AI 后完成时间增加 19% | 证明主观“更快”不可靠，必须测量真实周期 | 不能推导今天所有 AI 编码都会减速 |
| [NBER：Firm Data on AI](https://www.nber.org/papers/w34836) | 美、英、德、澳近 6,000 名企业高管 | 69% 企业使用 AI，但约九成报告过去三年对生产率或就业无影响 | 证明采用率不等于经营价值，孤立工具难以形成公司级结果 | 不能否定未来价值，也不能代替本公司试验 |
| [McKinsey：The State of AI 2025](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai-how-organizations-are-rewiring-to-capture-value) | 全球企业调查 | 在所测属性中，工作流重设计与 EBIT 影响关系最强；仅 21% 的 AI 使用组织重设计了部分工作流 | 支持“围绕工作流和经营结果建设”，不是只买模型 | 调查相关性不能证明 Hermes 必然产生 EBIT |
| [Stanford HAI：AI Index 2026](https://hai.stanford.edu/ai-index/2026-ai-index-report/economy) | 多来源全球数据 | 组织 AI 采用率达到 88%，但各业务职能的 Agent 部署大多仍为个位数 | 市场窗口存在，但企业 Agent 仍处早期 | 不能把行业采用率当成客户付费意愿 |
| [OpenAI：State of Enterprise AI 2025](https://openai.com/business/guides-and-resources/the-state-of-enterprise-ai-2025-report/) | 企业使用数据与约 9,000 名员工调查 | 用户自报每天节省约 40–60 分钟，结构化工作流使用增加 | 支持从临时问答转向重复工作流 | 属于供应商报告和自报数据，不能作为本项目 ROI 保证 |

### 3.2 研究给出的共同结论

研究并不支持“全面铺开 AI 即可降本增效”，但支持以下更克制的判断：

1. 边界明确、结果可检查、重复发生的任务，更容易取得价值；
2. 新手、低经验员工可能从优秀实践传播中获得更大收益；
3. 经验丰富者在复杂上下文中不一定受益，错误工具还可能增加检查成本；
4. 企业采用 AI 很普遍，但把 AI 变成企业级利润仍然少见；
5. 价值更多来自工作流和经营方式重构，而不是模型采购；
6. 主观节省时间不能代替任务周期、质量和财务结果；
7. 必须保留人工责任、评估、回滚和停用能力。

### 3.3 本项目的证据标准

外部研究只证明“值得验证”，不能证明“值得全面投资”。Hermes 的继续投资必须依靠
四级证据：

| 证据等级 | 证据内容 | 可支持的决策 |
|---|---|---|
| E0 观点 | 访谈、行业趋势、演示 | 只能立项调研 |
| E1 使用 | 活跃率、任务量、满意度 | 可以优化体验，不能确认 ROI |
| E2 运营 | 周期、吞吐、质量、返工、人工接管 | 可以扩大同类工作流 |
| E3 财务 | 增量贡献毛利、现金节省、可确认成本替代 | 可以扩大预算和商业推广 |

对老板的正式汇报必须区分 E1、E2 和 E3，不能把“很多人用了”描述成“已经创造
经营价值”。

## 4. 五种可选路线的实事求是对比

### 4.1 方案定义

| 方案 | 做法 |
|---|---|
| A. 保持现状 | 继续使用现有业务系统和人工协作 |
| B. 购买 AI 账号 | 给员工采购通用 AI 助手、办公套件或单点 Copilot |
| C. 分散集成 | 各部门分别开发 Bot、自动化脚本和 AI 应用 |
| D. 建设 AI 大中台 | 中央团队统一建设数据、模型、流程和超级入口 |
| E. Hermes 经营工作台 | 保留既有系统作为事实源，以连接、契约、员工 Agent 和能力资产层组织工作 |

### 4.2 决策对比

评分口径：高 / 中 / 低描述相对特征，不代替正式供应商报价和试点结果。

| 维度 | A 保持现状 | B 买账号 | C 分散集成 | D 大中台 | E Hermes |
|---|---|---|---|---|---|
| 首期投入 | 低 | 低 | 中 | 很高 | 中 |
| 上线速度 | 无变化 | 快 | 单点快 | 慢 | 首个工作流中等 |
| 个人任务效率 | 低 | 中至高 | 中至高 | 中 | 中至高 |
| 跨系统工作流 | 低 | 低至中 | 中 | 高 | 高 |
| 企业知识沉淀 | 低 | 低 | 分散 | 高 | 高 |
| 数据权限与审计 | 依赖原系统 | 能力不一 | 碎片化 | 可统一 | 中央统一、执行分布 |
| 对员工工作方式的适应 | 低 | 中 | 中 | 低至中 | 高 |
| 业务变化响应 | 慢 | 快但不成体系 | 单点快 | 依赖平台排期 | Skill、契约和视图可独立迭代 |
| 供应商锁定 | 既有系统锁定 | 较高 | 很高 | 高 | 通过协议和 Model Gateway 控制 |
| 长期维护 | 既有成本持续 | 账号和使用治理 | 接口与脚本膨胀 | 中央团队长期重 | 中等，目标随复用率下降 |
| 形成公司能力复利 | 低 | 低 | 低至中 | 中 | 高 |
| 失败时止损 | 容易 | 容易 | 单点容易、全局困难 | 困难 | 按工作流和能力包停用 |

### 4.3 为什么不是只买 AI 账号

购买通用账号适合：

- 文案、摘要、翻译、构思；
- 个人分析；
- 临时、低风险任务；
- 快速普及 AI 使用。

它难以独立解决：

- 多系统权威事实；
- 员工与员工 Agent 的正式协作；
- 带权限的企业知识；
- 可执行、可测试、可回滚的公司 Skill；
- 任务结果和财务结果追踪；
- 私有化、本地执行和设备控制；
- 一次优秀实践转为全公司能力。

因此，B 可以与 Hermes 并存。Hermes 不应重复建设一个通用聊天模型，而应组织
企业事实、任务、动作和能力。

### 4.4 为什么不是 AI 大中台

大中台的优势是统一，但常见代价是：

- 业务需求再次集中排队；
- 平台团队远离实际工作上下文；
- 所有人被迫使用统一页面和流程；
- 为覆盖全部业务提前建设大量抽象能力；
- 业务变化触发中央运行时改造；
- 平台本身成为长期固定成本。

Hermes 选择“中央薄治理、边缘厚智能”：

- 中央统一身份、事实、语义、权限、审计、模型路由和能力发布；
- 员工 Work Agent 结合个人任务上下文组织执行；
- 页面是可替换的读写方式，不是经营逻辑本身；
- 重复且验证有效的做法再进入公司知识和 Skill；
- 高风险动作保留人工确认和责任。

### 4.5 为什么不是分散开发很多 Bot

分散集成能快速形成局部效果，但容易产生：

- 重复账号、重复接口和重复数据副本；
- 每个 Bot 自己处理权限、重试、日志和版本；
- 无法解释哪个数据、Prompt、模型和规则产生了结果；
- 人员变动后脚本无人维护；
- 部门之间不能复用能力；
- 模型和 SaaS 变更导致批量返工。

Hermes 的价值不是集中所有业务代码，而是提供共同的治理和运行底座，让业务能力
以可版本化组件独立演进。

## 5. Hermes 的投资标的

### 5.1 不是再造现有业务系统

Hermes 不替代 CRM、ERP、财务、项目和电商平台的事实责任。它在这些系统之上建立
四层能力：

```text
第一层：安全连接
H5/PWA ↔ Remote Server ↔ Connector ↔ Hermes Agent

第二层：工作组织
Work Item + Task Contract + Agent-to-Agent Routing + Evidence

第三层：企业能力
Data Product + Knowledge + Skill + Action + View + Policy

第四层：经营闭环
内部效率与交付 + 外部 DTC+ 增长 + 结果反馈 + 能力进化
```

### 5.2 两种 Agent 的职责

| Agent | 服务对象 | 主要职责 | 不能做什么 |
|---|---|---|---|
| Work Agent | 员工 | 理解任务、组织信息、调用工具、协作、生成证据 | 不能越权，不能自行承担经营责任 |
| Evolution Agent | 企业 | 发现重复模式、提出知识和 Skill 候选、运行评估 | 不能未经 Owner 审批发布核心能力 |

两者形成双层迭代：

```text
员工完成真实工作
  → 产生 Outcome 与 Evidence
  → Evolution Agent 发现稳定模式
  → Owner 审核知识 / Skill / Action
  → 发布新版本
  → 更多 Work Agent 使用
  → 产生新的经营证据
```

### 5.3 双层 ILPO 保留经营责任

Hermes 不把企业经营交给 AI，而是把经营选择和执行明确分层：

| 层次 | ILPO | 责任主体 |
|---|---|---|
| Business ILPO | Insight / Leverage / Process / Output | 老板与业务 Owner |
| Execution ILPO | Input / Logic / Process / Output | 员工与 Work Agent |

二者通过 Task Contract 交接。Task Contract 至少明确：

- 目标和完成标准；
- 权威输入和版本；
- 可用 Skill、数据和动作；
- 权限、预算和时间边界；
- 人工确认点；
- 结果、证据和责任人；
- 失败、补偿和升级路径。

这使企业获得 AI 执行能力，同时不失去经营主权。

## 6. 从产品能力到经营价值的因果链

### 6.1 内部经营价值

```text
连接现有系统
  → 减少信息寻找和重复录入
  → Task Contract 明确责任与完成标准
  → Agent 路由减少等待和反复确认
  → Evidence 降低检查与交接成本
  → 知识和 Skill 复用减少重复劳动
  → 周期缩短、吞吐提高、返工下降
  → 释放产能、避免新增人力或改善交付现金流
```

不能从“时间节省”直接跳到“利润”。只有当节省时间被用于：

- 增加有效交付；
- 减少外包和加班；
- 避免新增编制；
- 缩短回款周期；
- 降低返工、事故和客户流失；
- 承接新增收入；

才进入财务收益。

### 6.2 外部 DTC+ 增长价值

```text
客户与渠道事实统一
  → 创作者、内容、广告、电商、零售形成同一 Work Item
  → Work Agent 加快洞察、素材适配和实验执行
  → Task Contract 约束品牌、预算、库存和授权
  → 订单、毛利、退货和复购回流
  → 识别真实增量而非渠道自报
  → 预算向高贡献毛利和高复购组合迁移
  → 形成客户资产与品牌资产
```

DTC+ 不是要求全部交易回到官网，而是以客户关系和经营结果连接：

- KOL：形成认知；
- KOC：建立信任；
- KOS：促进转化；
- KOA：在品牌和治理边界内规模化生成、适配和运营内容；
- Amazon、TikTok Shop、DTC 官网等电商渠道；
- 站内、站外和 Open Internet 广告；
- 线下零售和渠道合作；
- 售后、社群、会员和复购。

增长必须使用增量贡献毛利、客户获取成本、复购、退货、库存和现金共同判断。
曝光、内容量和 GMV 不能单独证明价值。

### 6.3 风险与治理价值

```text
统一身份和权限
  → 每次数据读取与动作都可判断
  → 高风险操作进入人工门禁
  → 全链路保留输入、版本、动作和结果证据
  → 错误可追踪、可暂停、可回滚
  → 降低影子 AI、数据外泄和自动化放大风险
```

风险价值只有在有历史事故、审计成本或可估算损失概率时才纳入 ROI。否则应作为
上线门槛，而不是虚构一笔“避免损失”收入。

### 6.4 企业能力复利

```text
一次有效执行
  → Evidence
  → 可引用 Knowledge
  → 可测试 Skill
  → 更多员工复用
  → 更多结果数据
  → 更好的版本
```

能力复利的前提不是保存所有工作内容，而是：

- 来源合法；
- 员工知情；
- 权限不被扩大；
- 有明确 Owner；
- 有适用范围和有效期；
- 能通过结果评估；
- 可以更正、撤回和停用。

## 7. 经营价值验证路径

### 7.1 总体路线

| 阶段 | 经营问题 | 主要交付 | 进入下一阶段的证据 |
|---|---|---|---|
| Gate 0 基线 | 问题是否足够大 | 基线、流程、数据和风险清单 | 成本池明确，Owner 与数据可用 |
| Gate 1 只读工作台 | AI 能否减少信息与协调摩擦 | 连接、检索、汇总、Task Contract、Evidence | 周期、质量、有效采纳改善 |
| Gate 2 低风险动作 | AI 能否进入正式执行 | 可回滚动作、Agent 路由、人工门禁 | 吞吐提升且错误受控 |
| Gate 3 能力资产 | 经验能否跨人复用 | Knowledge、Skill Registry、评估和版本 | 复用率、新人达标和一致性改善 |
| Gate 4 DTC+ 增长 | 能否创造外部经营收益 | 客户、内容、渠道、电商和复购闭环 | 增量贡献毛利和复购改善 |
| Gate 5 商业规模化 | 是否具备产品经济性 | 多租户、私有化、计费、客户成功 | 毛利、续费、交付周期和运维比率达标 |

### 7.2 Gate 0：经营基线与投资边界

周期：3–4 周。

必须完成：

1. 选择 1 个内部工作流；
2. 记录 4–6 周历史周期、触达时间、等待、返工和质量；
3. 确认 30–80 名试点员工与可比对照；
4. 确认 2–4 个系统、数据 Owner 和接口权限；
5. 定义财务价值承接方式；
6. 冻结 Task Contract v1；
7. 定义高风险动作和人工门禁；
8. 建立预算硬上限和停止条件。

Gate 0 退出条件：

- 没有可测量的高频工作流；
- 业务 Owner 不投入；
- 基线取不到；
- 数据授权无法完成；
- 节省产能没有承接方式；
- 现有 SaaS 以更低成本已能解决。

### 7.3 Gate 1：只读优先的内部试点

周期：8–12 周。

推荐首个场景：项目交付或客户服务协同。原因是：

- 任务频率高；
- 跨角色和跨系统；
- 结果和周期容易度量；
- 只读能力即可产生一部分价值；
- 比外部营销自动发布风险低；
- 产生的 Evidence 适合沉淀知识和 Skill。

最小能力：

- H5/PWA 访问；
- Remote Server 与 Connector 安全连接；
- Agent 状态和任务同步；
- 权限内跨系统检索与摘要；
- Work Item 与 Task Contract；
- 员工之间的 Agent 消息服务端路由；
- 来源、版本、确认和结果 Evidence；
- 运行、成本和质量观测。

不做：

- 全公司推广；
- 高风险自动执行；
- 自动发布企业核心 Skill；
- 自动对外发送内容；
- 大规模历史数据迁移；
- 复杂管理驾驶舱。

### 7.4 Gate 2：低风险动作与协作

满足 Gate 1 后再开放：

- 创建待办；
- 更新明确字段；
- 发起审批；
- 提交草稿；
- 请求其他员工或 Agent 提供材料；
- 在可撤销范围内安排标准动作。

每个 Action 必须具备：

- 最小权限；
- 幂等键；
- 状态机；
- 超时；
- 人工确认；
- 结果回执；
- 失败补偿或回滚；
- 审计证据；
- Owner 和版本。

### 7.5 Gate 3：知识和 Skill 复用

只把重复出现、结果稳定、边界明确的做法升级为公司能力。

发布条件：

- 至少有多个真实 Work Item 证据；
- 质量达到业务 Owner 设定的阈值；
- 使用的数据和知识具有合法权限；
- 异常、成本和人工接管率可接受；
- 有回归测试和上一稳定版本；
- 有 Owner、有效期和停用条件。

核心指标：

```text
Capability Reuse Rate
  = 使用已发布能力完成的有效 Work Item
  / 适用 Work Item 总数
```

必须与结果质量共同观察，不能追求低质量能力的高复用。

### 7.6 Gate 4：DTC+ 外部增长

推荐从单一产品、单一区域或单一客户群开始，避免全渠道同时改造。

第一期只选一条可归因路径，例如：

```text
特定客户群
  → 2–3 类内容主张
  → 2 个投放 / 创作者渠道
  → 1 个成交渠道
  → 售后和 60/90 天复购
```

验证方法优先级：

1. 随机对照；
2. 地域或客户群 Holdout；
3. 差分中的差分；
4. 上线前后对比并控制季节和促销；
5. 仅在无法建立对照时使用平台归因。

扩大的条件不是内容增多，而是：

- 增量贡献毛利为正；
- CAC 在目标范围内；
- 退货和投诉未恶化；
- 复购或客户价值改善；
- 库存、履约和现金承接得住；
- 品牌和数据合规通过。

### 7.7 Gate 5：商业产品化

只有客户价值被证明后，再承担：

- 多租户运营；
- 套餐、权益和计费；
- 客户成功和支持；
- SaaS、专有云、私有化与离线交付；
- 安全合规认证；
- 渠道合作；
- 规模容量和灾备；
- 标准实施方法。

此阶段验证的是 Hermes 自身商业价值：

| 指标 | 含义 |
|---|---|
| ARR / 合同额 | 收入规模 |
| 毛利率 | 扣除模型、云、交付和支持后的产品经济性 |
| 实施周期 | 从签约到首个经营结果的时间 |
| Time to First Value | 客户首次取得 E2/E3 证据的时间 |
| 续费与扩容 | 客户是否持续认可价值 |
| 能力复用率 | 标准组件而非定制开发的占比 |
| 支持工时 / 客户 | 维护是否随客户数线性增长 |
| 版本一致率 | 是否避免多套分支 |

## 8. 试点设计与验收

### 8.1 推荐试点 A：内部项目交付

适用对象：

- 售前到交付；
- 产品研发协同；
- 客户问题处理；
- 采购或财务资料流转；
- 跨部门经营分析。

建议分组：

| 组别 | 使用方式 |
|---|---|
| 对照组 | 保持当前系统和流程 |
| 试点组 | 使用 Hermes 工作台、Task Contract 与只读 Agent |

若无法随机分组，应至少选择历史表现相近的团队，并记录业务量、人员经验和任务难度。

### 8.2 试点 A 指标

| 指标 | 定义 | 目标设置原则 |
|---|---|---|
| 端到端周期 | 创建到正式完成 | 以历史中位数为基线 |
| 有效触达时间 | 实际处理任务的时间 | 与等待时间分开 |
| 等待时间 | 等材料、等确认、等系统 | 验证协调价值 |
| 一次通过率 | 不返工完成的比例 | 防止以速度换质量 |
| 结果错误率 | 经确认的实质错误 | 必须设上限 |
| 人工接管率 | Agent 无法完成或被接管 | 用于确定自动化边界 |
| 有效采纳率 | 输出被确认且产生预期结果 | 不用登录率替代 |
| 单 Work Item 成本 | 人工、模型、系统和复核成本 | 判断规模化经济性 |
| 员工信任 | 愿意纠错、授权和继续使用 | 不监控私人内容 |

### 8.3 推荐试点 B：DTC+ 增长

试点 A 通过后，再选择一个低品牌风险的产品线开展。

| 环节 | Hermes 工作 |
|---|---|
| 洞察 | 汇总客户反馈、搜索、渠道和竞品事实 |
| 内容 | 生成受品牌约束的多渠道草稿 |
| 协作 | KOL、KOC、KOS、KOA 和内部员工按 Task Contract 协作 |
| 投放 | 在预算和审批边界内生成实验任务 |
| 成交 | 连接电商、官网或零售结果 |
| 复购 | 连接服务、会员、复购和客户授权 |
| 学习 | 把实验结果回流为知识和 Skill 候选 |

### 8.4 试点 B 指标

| 层次 | 指标 |
|---|---|
| 效率 | 内容从需求到上线周期、实验启动周期、人工复核成本 |
| 品牌 | 不合规率、人工驳回率、投诉、负面反馈 |
| 获客 | 增量触达、有效线索、增量新客、CAC |
| 盈利 | 增量贡献毛利、渠道费、退货、履约和服务成本 |
| 客户 | 首购转复购、60/90/180 天留存、客户价值 |
| 组织 | 有效 Skill 复用、跨市场适配时间、Evidence 完整率 |

### 8.5 统一 Gate 结果

| 结果 | 条件 | 决策 |
|---|---|---|
| GO | 主要经营指标改善，质量与风险合格，单位经济性可扩展 | 扩大相邻工作流 |
| CONDITIONAL | 有局部价值，但数据、成本或流程存在可修复问题 | 限时修复后复测 |
| HOLD | 结果不稳定或承接能力不足 | 暂停扩张，保留底座 |
| STOP | 无可测价值、风险越界或复核成本吃掉收益 | 停用该能力，回滚 |

## 9. ROI 与 TCO：只计算能兑现的价值

### 9.1 收益模型

```text
年度经营收益
  = 可兑现产能价值
  + 增量贡献毛利
  + 可确认成本替代
  + 可估算避免损失
  + 现金周期改善价值
```

其中：

```text
可兑现产能价值
  = 适用员工数
  × 年有效工作日
  × 每日净节省时间
  × 全成本小时单价
  × 有效采纳率
  × 产能兑现系数
```

`产能兑现系数`必须小于或等于 1，用来排除“节省了时间但没有增加产出或减少成本”
的部分。

```text
增量贡献毛利
  = 增量收入
  - 商品 / 服务变动成本
  - 渠道和投放成本
  - 履约、退货和售后变动成本
```

不能用 GMV 或平台归因收入代替增量贡献毛利。

### 9.2 总拥有成本

```text
年度 TCO
  = 产品研发摊销
  + 云与网络
  + 模型调用
  + 数据与搜索
  + 安全与合规
  + 人工复核
  + Skill / 知识 Owner 运营
  + 客户实施与支持
  + 事故和升级
  + 旧系统重叠成本
  - 被停用系统和接口的成本
```

AI 工作台常被低估的不是模型费，而是复核、数据治理、接口变化和旧系统长期并存。
这些成本必须在 Gate 1 就开始记录。

### 9.3 ROI 和回收期

```text
年度 ROI
  =（年度经营收益 - 年度 TCO）/ 年度 TCO

投资回收期（月）
  = 初始投资 / 月度净经营收益
```

对试点阶段，优先使用“单位 Work Item 成本”和“达到 E2/E3 证据的成本”，避免
用尚未稳定的年度外推支持大额预算。

### 9.4 三种示例情景

以下仅演示计算方式，不是收益承诺。

共同假设：

- 年有效工作日 220 天；
- 时间收益已经扣除使用和复核时间；
- 不计增长和风险收益；
- 年度 TCO 包含模型、云、维护、治理和复核；
- 产能价值只有被有效承接后才计算。

| 情景 | 员工 | 日净节省 | 小时成本 | 有效采纳 | 兑现系数 | 年产能价值 | 年 TCO | 净收益 / ROI |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 小范围 | 50 | 15 分钟 | ¥100 | 50% | 70% | ¥96,250 | ¥300,000 | -¥203,750 / -68% |
| 基准 | 150 | 30 分钟 | ¥120 | 65% | 70% | ¥900,900 | ¥720,000 | ¥180,900 / 25% |
| 规模化 | 500 | 45 分钟 | ¥150 | 75% | 80% | ¥7,425,000 | ¥2,000,000 | ¥5,425,000 / 271% |

该表说明两点：

1. 小范围内部效率工具可能无法覆盖企业级平台成本；
2. 规模、采纳和兑现能力决定 ROI，不能只追求单次演示效果。

若 Hermes 只能节省少量个人时间，应使用标准 SaaS；只有当它进入高频工作流、
减少协调成本并形成可复用能力时，企业级投资才有经济性。

### 9.5 盈亏平衡

内部效率场景的最低日节省时间可反推：

```text
盈亏平衡日节省分钟
  = 年度 TCO × 60
  /（员工数 × 工作日 × 小时成本 × 有效采纳率 × 兑现系数）
```

在每个预算 Gate 前，CFO 应用最新真实数据重算。若所需节省时间超过业务可实现
范围，应停止或转向增长价值更明确的场景。

## 10. 分阶段投资预算

### 10.1 预算口径

使用人月而不是一次性总价，便于不同组织按真实成本核算：

```text
阶段预算
  = 研发与产品人月 × 全成本人月单价
  + 云 / 模型 / 数据 / 安全现金支出
  + 业务 Owner 和试点员工机会成本
  + 风险准备金
```

### 10.2 阶段预算区间

| 阶段 | 周期 | 人月 | 主要现金支出 | 批准方式 |
|---|---:|---:|---|---|
| Gate 0 基线与契约 | 3–4 周 | 2–4 | 调研、必要顾问或测试工具 | 固定上限 |
| Gate 1 商用底座 + 内部试点 | 8–12 周 | 10–16 | 云、模型、安全测试 | 里程碑付款 |
| Gate 2 动作与协作 | 8–12 周 | 12–20 | 集成、审计、灰度环境 | E2 证据后批准 |
| Gate 3 企业能力层 | 12–16 周 | 18–30 | 搜索、评估、知识治理 | 复用价值后批准 |
| Gate 4 DTC+ 增长 | 12–16 周 | 15–25 | 渠道连接、实验预算 | 增量毛利门禁 |
| Gate 5 商业规模化 | 单独立项 | 30–60+ | 多租户、私有化、认证和运营 | E3 与客户签约后批准 |

以上阶段可以部分重叠，但不能跳过经营门禁。人数增加不应替代范围收敛。

### 10.3 资金释放规则

每一阶段只释放到下一个可验证节点：

- 先有基线，再建设；
- 先有只读结果，再开放动作；
- 先有多次真实 Evidence，再发布 Skill；
- 先有贡献毛利，再扩大 DTC+；
- 先有客户复购和标准交付，再扩展商业团队。

任何阶段预算超出 20%，必须重新提交：

- 超支原因；
- 未完成范围；
- 已取得证据；
- 删除或延期项；
- 新的回收期和退出成本。

### 10.4 分阶段投资的财务意义

Gate 0 和 Gate 1 的首要产出不只是软件，而是降低三项不确定性：

- 客户或内部员工是否真实使用；
- 工作流能否产生 E2 运营改善；
- 改善能否兑现为 E3 财务结果。

因此，首期投资应被视为一项有上限的“验证选择权”。如果结果成立，公司获得继续
扩大的权利；如果结果不成立，公司以有限成本停止，而不是因为已经建设了大平台而
被迫继续投入。

需要进行三年以上规模化投资时，可增加风险调整净现值：

```text
风险调整 NPV
  = Σ［第 t 年实现概率 × 第 t 年经营收益 - 第 t 年 TCO］
      /（1 + 资本成本）^t
  - 初始投资
```

实现概率必须随 Gate 证据更新，不能在立项时直接按 100% 计算。

## 11. 低维护成本不是少做治理，而是减少变化扩散

### 11.1 维护成本目标

不承诺“零维护”。目标是让业务变化主要发生在数据契约、Knowledge、Skill、
Action、Policy 和 View 中，而不是每次修改 Agent 运行时和所有客户端。

维护成本可以用下式观察：

```text
单位能力维护成本
  = 该能力年度变更、评估、故障、复核和升级工时
  / 该能力产生的有效 Work Item
```

随着复用量提高，该指标应下降；若长期上升，说明能力设计或适用范围错误。

### 11.2 四条独立发布列车

| 发布对象 | 变化原因 | 发布节奏 | 降低维护的方式 |
|---|---|---|---|
| Hermes Agent Runtime | 模型、工具、安全和执行能力 | 稳定、受控 | Local Gateway 版本契约 |
| Connector | 连接、重试、本地状态和升级 | 稳定、独立 | 只认识 Hermes WSS，不暴露内部消息设施 |
| Remote Server | 多租户、路由、事实、审计和运营 | 服务端持续 | 兼容当前与前两代 Connector |
| Capability Packages | Skill、Knowledge、Action、Policy、View | 业务可较快迭代 | Registry、版本、评估和回滚 |

Agent 更新不应要求 Connector、H5 和全部业务能力同步更新；公司 Skill 变化也不应
要求重发 Agent 安装包。

### 11.3 稳定协议隔离变化

低维护架构依靠：

- Connector Protocol；
- Local Gateway Protocol；
- Task Contract；
- Work Event；
- Data Product Contract；
- Skill Manifest；
- Action Contract；
- Policy 和 Evidence Schema。

同一 Major 版本只增加兼容字段和 capability；破坏性变更使用并行版本和迁移窗口。
客户端按 capability 判断能力，不根据版本字符串猜测。

### 11.4 不让基础设施泄漏到客户端

Connector 只连接 Hermes Remote Server 的 WSS，不直接连接 Redis、NATS、
PostgreSQL 或对象存储。

这样可以：

- 服务端替换消息或存储设施时不升级全部 Connector；
- 保留 Hermes 对外协议控制权；
- 降低客户设备上的依赖和故障面；
- 避免将服务端凭证分发到终端；
- 把多租户、路由、重放和审计集中运营。

中国大陆商用首发按既有架构选择阿里云承载 WAF、负载均衡、容器、PostgreSQL、
对象存储、密钥和可观测能力；这些产品通过基础设施适配层接入，不进入 Connector
Protocol、Task Contract 和 Skill 契约。由此保留后续议价、迁移和私有化交付空间。

### 11.5 一套代码，多种部署

SaaS、专有云、私有化和离线版共用：

- 同一领域代码；
- 同一协议和 Schema；
- 同一镜像和制品；
- 同一 Migration；
- 同一评估和测试基线。

差异通过部署配置、基础设施适配、密钥和能力开关表达。禁止为四种交付模式维护
四套业务分支。

### 11.6 Model Gateway 隔离模型变化

Skill 不绑定某个模型品牌，而声明：

- 任务能力要求；
- 数据边界；
- 时延上限；
- 成本上限；
- 质量阈值；
- 降级策略。

Model Gateway 根据租户、场景、合规和成本选择模型。更换模型时先运行回归评估，
而不是修改全部 Skill。

### 11.7 资产化替代定制化

客户差异优先通过可配置和可版本化资产交付：

- Data Product；
- Metric；
- Knowledge；
- Skill；
- Action；
- View；
- Policy；
- Task Contract Template。

只有无法抽象且具有足够合同价值的需求才进入定制代码。每个定制需求必须回答：

1. 是否能成为标准组件；
2. 是否由配置解决；
3. 后续由谁维护；
4. 客户是否承担持续成本；
5. 停用后如何迁移。

### 11.8 自动评估与灰度

每个核心 Skill 和 Action 发布前运行：

- 固定样本回归；
- 权限越界测试；
- 引用和版本检查；
- 成本和超时测试；
- 对抗和异常输入；
- 人工门禁测试；
- 上一版本对比；
- 回滚演练。

生产发布使用小流量、少租户或少团队灰度。错误预算耗尽、UNKNOWN 状态异常、
人工接管激增或单位成本越界时自动暂停扩大。

### 11.9 Evolution Agent 降低内容维护，不取消责任

Evolution Agent 可自动：

- 发现重复问题；
- 识别失效知识；
- 生成 Skill 更新候选；
- 组织评估样本；
- 对比版本效果；
- 提醒 Owner 审核和停用；
- 发现重复页面和接口。

它不能自动：

- 扩大数据权限；
- 发布核心 Skill；
- 修改高风险 Action；
- 删除正式 Evidence；
- 改变经营口径；
- 代替 Owner 承担责任。

### 11.10 主动退出旧成本

新平台上线后若旧页面、脚本、报表和接口全部保留，TCO 只会增加。

每个成功工作流必须附带退役清单：

| 退役对象 | 触发条件 | 责任人 |
|---|---|---|
| 重复手工报表 | 新结果连续稳定 2–3 个周期 | 报表 Owner |
| 临时接口 / 脚本 | 标准 Action 或 Data Product 覆盖 | 技术 Owner |
| 重复知识库 | 权限、引用和迁移验证完成 | 知识 Owner |
| 旧工作页面 | 新 View 覆盖角色任务且可回退 | 产品 Owner |
| 重复 AI 账号 / Bot | 使用、合同和数据迁移完成 | 采购与 IT |

节省必须来自“新能力替代旧成本”，而不是“在旧成本上叠加 AI”。

### 11.11 低维护运行指标

建议每月查看：

| 指标 | 目标方向 |
|---|---|
| 配置 / 契约 / 能力包完成的变更占比 | 上升 |
| 修改核心 Runtime 的业务需求占比 | 下降 |
| 自动回归覆盖的核心 Skill 占比 | 上升 |
| 每客户定制代码量 | 下降 |
| 支持工时 / 活跃客户 | 稳定或下降 |
| 单有效 Work Item 模型与基础设施成本 | 下降 |
| N / N-1 / N-2 版本兼容率 | 保持 |
| 回滚平均时间 | 下降 |
| 无 Owner 或过期资产数量 | 接近零 |
| 被正式退役的旧页面、脚本和接口 | 持续增加 |

### 12.1 最小治理结构

| 角色 | 必须承担的结果 |

| CEO / 经营赞助人 | 选择价值池、解决跨部门冲突、决定投资门禁 |

| 安全与合规 | 身份、最小权限、审计和事件处置 |
| 平台 Owner | 协议、运行时、可用性、成本和发布 |
| 员工代表 | 使用体验、知情边界、纠错和信任 |

### 12.2 投资人与 CEO 侧的治理动作

该侧只需要对经营边界和资本结果负责：

- 选择一个足够重要但风险可控的价值池；
- 指定能够跨部门负责的业务 Owner；
- 要求财务先建立基线；
- 允许流程被重设计；
- 确认员工知情、纠错和申诉边界；
- 每个 Gate 只看经营证据和风险；
- 对没有结果的能力及时停用；
- 把节省的产能安排到明确结果上。

模型、Prompt 和页面细节由产品与技术团队承担；采用不以员工排行榜或私人工作
监控推动。

## 13. 主要风险与控制

| 风险 | 早期信号 | 控制 |
|---|---|---|
| 使用很多但没有经营价值 | 登录和消息增加，周期不变 | 只认可 E2/E3 证据 |
| AI 让专家更慢 | 复核时间和接管率上升 | 按角色分组，不强制统一使用 |
| 错误被规模化 | 错误率、返工、投诉上升 | 只读起步、人工门禁、灰度和回滚 |
| 数据权限失控 | Agent 引用无权数据 | 查询和动作时双重鉴权，权限不继承扩大 |
| 员工抵触 | 隐瞒工作、不纠错、绕开系统 | 明确知情范围，不采集私人内容，不做隐性排名 |
| 平台再次中央化 | 业务持续等待平台排期 | 稳定契约 + 分布式 Work Agent + Capability Packages |
| 定制项目失控 | 每客户出现独立分支 | 单一代码线、配置优先、定制审批 |
| 模型或供应商锁定 | Skill 写死模型和专有接口 | Model Gateway、标准协议、可移植资产 |
| 云与模型成本失控 | 单 Work Item 成本持续上升 | 预算限额、模型路由、缓存、批处理和降级 |
| DTC+ 虚假增长 | GMV 上升但毛利、复购下降 | 增量贡献毛利、Holdout 和客户队列 |
| 知识和 Skill 过期 | 错误引用、人工纠正增加 | Owner、有效期、评估、撤回和停用 |
| 新旧系统长期重叠 | TCO 上升 | 每个工作流绑定退役清单 |

## 15. 最终建议

### 15.1 投资理由

Hermes 的合理投资逻辑不是“做一个更强的 AI 助手”，而是建立一层低耦合的企业
经营执行基础：

1. 连接现有事实系统，不先替换它们；
2. 用 Task Contract 把经营选择转为可执行、可验证的工作；
3. 让员工 Work Agent 在权限内组织跨系统和跨角色协作；
4. 让结果形成 Evidence，而不是只留下聊天记录；
5. 把经过验证的实践沉淀为知识和 Skill；
6. 以 DTC+ 把外部内容、渠道、成交和复购连接到贡献毛利；
7. 用稳定协议、独立发布、能力包和自动评估控制维护成本；
8. 用每阶段的经营证据决定下一笔资本投入。

### 15.2 建议的批准意见

建议投资委员会作出以下决定：

> 批准 Hermes Gate 0 与 Gate 1，预算按 12–20 人月及外部现金支出硬上限管理。
> 试点限定为一个内部高频跨系统工作流，以 12–16 周完成经营价值验证。
> 未取得周期、质量、有效采纳和单位经济性改善，不进入动作自动化、企业能力层和
> DTC+ 扩张。后续每一阶段单独审批，不以已投入成本作为继续投资理由。

### 15.3 成功的定义

Hermes 成功不表现为：

- 员工每天发送更多 AI 消息；
- 系统中出现更多 Agent；
- 自动生成更多页面和内容；
- 管理层看到更多报表；
- 企业宣布完成 AI 转型。

成功必须表现为：

- 一个重要工作流更快、更稳定、更便宜；
- 员工减少寻找、搬运、等待和重复确认；
- 组织把有效经验变成可复用能力；
- 外部增长能够回到贡献毛利、客户和复购；
- 新能力替代一部分旧页面、脚本、接口和人工维护；
- 客户愿意持续付费，且支持成本不随客户数同比增长；
- 每一轮运行都为下一轮提供更可靠的数据、知识和 Skill。

这时，Hermes 才不是一项需要持续输血的 AI 项目，而是一套能够通过经营结果证明
自身、通过能力复用降低边际成本、通过双层 Agent 持续进化的企业工作基础。
